Section 2.1

VS Code Process Topology

Recruiters often ask why VS Code is extremely stable and doesn't freeze the whole computer when a plugin crashes. The secret is its multi-process architecture.

Unlike older editors that run everything inside a single memory block, VS Code separates tasks into isolated workers:

1. The Main / Renderer Process
Renders the visual interface (buttons, text editor boxes, scrollbars). Built on Electron (Chromium browser runtime).
Interprocess Communication (IPC)
2. Extension Host Process
A separate background process where all your plugins (Prettier, GitLens, Python) execute. If a plugin crashes, your window stays completely responsive!
Spawns shell subprocesses
3. Terminal Process (Node PTY)
Runs shell processes (PowerShell, Bash) in the background and pipes text inputs/outputs directly to the main visual screen.
Section 2.2

Node.js Runtime Under the Hood

Node.js is not a programming language—it is a runtime. It takes the JavaScript language (which traditionally only runs inside browsers) and allows it to run directly on your computer's operating system.

Under the hood, Node is built using two core engines:

  • V8 Engine: Created by Google for Chrome. It takes your raw JavaScript text and compiles it into low-level machine instructions (assembly binary code) using Just-In-Time (JIT) compilation.
  • libuv: A multi-platform C library that handles the event loop, file operations, system processes, and network requests asynchronously in the background.
10th Grade Analogy: The Cook & The Helpers

Think of the V8 engine as the Head Cook in a kitchen. The cook reads order sheets (your code) and quickly translates them into instructions. The cook only has one workspace (single-threaded execution). However, if an order takes a long time (like baking a cake or fetching data from a database), the Cook hands that ticket to the helper staff—libuv. The helper staff works in the background (multithreaded operations) and calls the Cook back (using callback queues) once the cake is fully baked, keeping the main cook free to accept more tickets!

Section 2.3

Git Content-Addressable Storage

Git does not track changes as simple delta lines. Instead, Git behaves like a local transactional database. Inside your hidden .git folder, Git maps your files into a Directed Acyclic Graph (DAG) using cryptographic hash keys.

Git categorizes everything into three core object types:

Git Object Type Under-the-Hood Database Behavior
Blobs Stores raw file contents (pure data bytes). Blobs do not know their own filename, folder paths, or timestamps! They only contain content data.
Trees Stores directory trees. A Tree acts like a folder log, linking blob hashes to physical filenames, permissions, and directory trees.
Commits A metadata snapshot points to a single root Tree hash, referencing author names, timestamps, parent commits, and description comments.

Every file is cryptographically signed using SHA-1 (or SHA-256) hash functions. If you change a single letter in a file, its hash code changes completely. Git detects this instantly, creating a new Blob object and linking it in the directory graph.

Section 2.4

The Environmental PATH Resolution

When you type git, node, or npm in your terminal, how does the computer know what program to run? It relies on the PATH environment variable.

The PATH is a list of directory paths stored in your operating system's memory. When a command is entered, the shell executes a lookup sequence:

Command Resolution Loop System Logic 
User enters command: "node --version"
 ↓
Shell looks at system environment variable: $PATH
 ↓
Shell scans list of paths in order:
  1. C:\Windows\system32? No 'node.exe' found.
  2. C:\Windows? No 'node.exe' found.
  3. C:\Program Files\nodejs? YES! Found 'node.exe' here.
 ↓
Shell executes "C:\Program Files\nodejs\node.exe --version"
 ↓
Prints version: v18.16.0

If you receive the error "command not found" or "is not recognized as an internal or external command", it simply means the directory where the program's executable is stored is not listed inside your environment PATH variable list!
